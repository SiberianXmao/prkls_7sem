# Практическая работа №1. Многопоточность и параллельные вычисления

Дисциплина: «Проектирование и разработка клиент-серверных приложений».



Проект рассчитан на Java 25, Maven и JUnit 5. Все случайные входные данные
создаются с фиксированным `seed = 272026`, поэтому сравниваемые реализации
получают одинаковую нагрузку.

## Задание 1. Обработка массива

Один массив из 50 000 000 значений создаётся до замеров и затем используется
всеми реализациями. Реализованы:

1. последовательный проход;
2. непересекающиеся диапазоны в `ExecutorService`;
3. рекурсивное деление диапазона в `ForkJoinPool`.

Число worker-потоков равно `Runtime.getRuntime().availableProcessors()`:
это разумная исходная точка для CPU-bound нагрузки, потому что увеличение
числа вычисляющих потоков сверх числа доступных процессоров обычно лишь
увеличивает переключения контекста. Для `ForkJoinPool` проверяются пороги
25 000, 100 000 и 500 000 элементов.

Контрольный запуск: 50 000 000 элементов, 20 доступных процессоров, два
warm-up-запуска и пять измеряемых запусков.

| Реализация | Среднее, мс | Медиана, мс | Ускорение по медиане |
|---|---:|---:|---:|
| Последовательная | 9,239 | 9,068 | 1,00 |
| ExecutorService, 20 workers | 7,550 | 7,089 | 1,28 |
| ForkJoin, threshold 25 000 | 7,084 | 6,909 | 1,31 |
| ForkJoin, threshold 100 000 | 6,714 | 6,721 | 1,35 |
| ForkJoin, threshold 500 000 | 6,667 | 6,223 | 1,46 |

Все реализации вернули одинаковый минимум: `-2147483575`. Лучший результат
в этом запуске показал `ForkJoinPool` с порогом 500 000. Ускорение не является
линейным: поиск минимума очень прост, поэтому на коротком вычислении заметны
расходы на создание пула, постановку задач, синхронизацию, объединение
частичных результатов и доступ к памяти. Отдельные запуски также зависят от
JIT-компиляции, планировщика ОС и фоновой нагрузки, поэтому в таблице
используется медиана, а исходные времена программа печатает полностью.

## Задание 2. Platform Threads и Virtual Threads

Заранее создаются 750 одинаковых спецификаций задач. Каждая задача делает
небольшое вычисление, блокируется в `Thread.sleep()` на 20–80 мс, имитируя
ожидание внешнего ресурса, и возвращает ID с контрольной суммой.

Сравниваются fixed pool из 50 platform threads и один virtual thread на задачу.
Параметры fixed pool ограничивают число одновременно занятых системных
потоков и не создают сотни дорогих platform threads.

| Executor | Задач | Параметры | Среднее общее время, мс |
|---|---:|---|---:|
| Fixed thread pool | 750 | pool = 50, задержка 20–80 мс | 814,969 |
| Virtual thread per task | 750 | задержка 20–80 мс | 92,943 |

В контрольном запуске virtual threads обработали набор примерно в 8,77 раза
быстрее. Platform thread остаётся занятым на всём интервале блокировки, а
virtual thread может быть размонтирован с carrier thread. Это позволяет
обслуживать много ожидающих задач без такого же количества системных потоков.
Для чистых CPU-bound вычислений такого преимущества не было бы.

## Задание 3. CompletableFuture

Предметная операция вычисляет стоимость заказа с учётом количества и скидки.
Цепочка имеет вид:

```text
Input -> Validation -> Calculation -> Transformation -> Result
```

Валидация выполняется через `thenApply`, асинхронное вычисление возвращает
новый `CompletableFuture` и подключается через `thenCompose`, после чего
результат форматируется. `orTimeout` ограничивает время цепочки, а `handle`
превращает ошибку в понятный `RequestResult` с ID исходного запроса.

Все цепочки создаются до `CompletableFuture.allOf(...).join()`, поэтому основной
поток не ждёт каждый запрос перед отправкой следующего. Собственный executor
корректно завершается через `AutoCloseable`.

## Задание 4. Producer / Consumer

Выбрана архитектура общего пула consumers с маршрутизацией по `FileType`.
Producer помещает XML/JSON/XLS-задачи размером 10–100 единиц в ограниченную
`ArrayBlockingQueue`. Если producer работает быстрее, `put()` блокируется и
естественно создаёт backpressure; проверки `isEmpty()` в цикле нет.

Завершение конечное: после данных producer кладёт по одному poison pill на
каждого consumer. `InterruptedException` обрабатывается явно. Для конкурентной
статистики используются `LongAdder` и concurrent-наборы ID.

Контрольный результат:

```text
Generated: 30
Processed: 30
XML: 10
JSON: 10
XLS: 10
Total processing time: 1053 ms
```

После завершения программно проверяются инварианты:

- `Generated = Processed`;
- `Processed = XML + JSON + XLS`;
- множества созданных и обработанных ID совпадают;
- повторная обработка одного ID приводит к ошибке.
