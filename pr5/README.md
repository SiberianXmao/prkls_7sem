# Практическая работа №5 — контейнеризация распределённого приложения

Проект представляет собой небольшую систему оформления заказов и доставок.
Она состоит из двух Spring Boot-сервисов, PostgreSQL и Traefik и полностью
запускается одной командой Docker Compose.

## Архитектура

```text
                         http://localhost:8080
                                  │
                                  ▼
                              Traefik
                         ┌────────┴────────┐
                         │                 │
              /api/orders/**     /api/deliveries/**
                         │                 │
                         ▼                 ▼
                  Order Service      Delivery Service
                    1 экземпляр        3 экземпляра
                         ▲                 │
                         └──── REST ───────┘
                         │                 │
                         └────────┬────────┘
                                  ▼
                              PostgreSQL
                     schemas: orders, deliveries
```

При создании доставки `Delivery Service` сначала запрашивает заказ у
`Order Service` через Spring `RestClient`, проверяет его состояние, а затем
сохраняет доставку в своей схеме.

| Компонент | Ответственность |
|---|---|
| `order-service` | создание, чтение и изменение статусов заказов |
| `delivery-service` | проверка заказа, создание и отслеживание доставки |
| PostgreSQL | постоянное хранение данных в двух изолированных схемах |
| Traefik | единая внешняя точка входа, маршрутизация и балансировка |

## Разделение ответственности внутри сервисов

Оба приложения используют одинаковое разделение на слои:

- `api` — тонкие REST-контроллеры, DTO и обработчики HTTP-ошибок;
- `service` — бизнес-правила и границы транзакций;
- `repository` — интерфейсы Spring Data JPA;
- `domain` — JPA-сущности и допустимые переходы состояний;
- `config` и `support` — конфигурация времени, HTTP-клиента и ID экземпляра;
- `client` — изолированный клиент межсервисного взаимодействия.

Контроллеры не работают с БД и не содержат бизнес-логику. Структура таблиц
создаётся миграциями Flyway, а Hibernate работает в режиме `validate` и не
изменяет схему самостоятельно.

## База данных

Используется один полноценный контейнер PostgreSQL с двумя схемами предметных
областей:

- `orders.customer_orders` — заказы;
- `deliveries.deliveries` — доставки;
- по одной таблице `flyway_schema_history` в каждой схеме.

Между таблицами намеренно нет внешнего ключа: сервисы взаимодействуют через API,
а не обращаются к чужим таблицам. Поле `order_id` в доставках уникально на уровне
PostgreSQL, поэтому две реплики не смогут одновременно создать две доставки для
одного заказа. Сущности также содержат поле `version` для optimistic locking.

## Запуск

Из каталога `pr5` выполнить:

```powershell
docker compose up --build -d
docker compose ps
```

При первом запуске Docker скачивает образы и Maven-зависимости, поэтому сборка
может занять несколько минут. Compose дождётся готовности PostgreSQL и сервисов
по healthcheck, после чего запустит Traefik.

Доступные адреса:

- API через Traefik: <http://localhost:8080>;
- панель Traefik: <http://localhost:8081/dashboard/>;
- PostgreSQL с хоста: `localhost:5435`.

Все порты и параметры PostgreSQL находятся в `.env`. Приложения получают URL,
пользователя и пароль только через переменные окружения; адреса не зашиты в
Java-код.

## REST API

### Order Service

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/api/orders` | создать заказ |
| `GET` | `/api/orders` | получить все заказы |
| `GET` | `/api/orders/{id}` | получить заказ по ID |
| `PATCH` | `/api/orders/{id}/status` | изменить статус заказа |

Допустимые статусы: `NEW`, `CONFIRMED`, `CANCELLED`.

### Delivery Service

| Метод | Маршрут | Назначение |
|---|---|---|
| `POST` | `/api/deliveries` | создать доставку для существующего заказа |
| `GET` | `/api/deliveries` | получить все доставки |
| `GET` | `/api/deliveries/{id}` | получить доставку по ID |
| `PATCH` | `/api/deliveries/{id}/status` | изменить статус доставки |
| `GET` | `/api/deliveries/instance` | показать экземпляр, обработавший запрос |

Допустимые статусы: `CREATED`, `IN_TRANSIT`, `DELIVERED`, `CANCELLED`.

Ошибки возвращаются в формате `application/problem+json` с корректными HTTP-кодами:
`400`, `404`, `409`, `422` или `503`.
